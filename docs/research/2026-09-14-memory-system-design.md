# Системный дизайн памяти Browser-Harness агента

Дизайн адаптирует архитектурные паттерны Claude Code (иерархия CLAUDE.md, авто-память, компакция как транзакция), Codex CLI (AGENTS.md, внешние memory-серверы поверх MCP) и общую индустриальную модель памяти агентов (working / semantic / procedural / episodic) под специфику агента, управляющего браузером.

---

## 1. Базовые принципы (заимствованные)

- **Сессия эфемерна, память — нет.** Всё, что должно пережить сессию, должно жить вне контекстного окна, во внешнем хранилище.
- **Файлы, а не векторная БД по умолчанию.** Простой, диффуемый, человекочитаемый markdown как источник истины; векторный/графовый поиск — опциональная надстройка поверх файлов, не замена им.
- **Явный memory-tool, а не скрытый RAG.** Агент сам решает, что читать/писать (view / create / str_replace / insert / delete / rename над директорией `/memory`), а не получает "магически" подмешанный контекст без своего ведома.
- **Компакция — это транзакция.** Сжатие истории диалога не должно быть единственным путём восстановления состояния; параллельно поддерживается дешёвый "дайджест сессии", который не пересчитывается с нуля в момент переполнения контекста.
- **После компакции — перечитать авторитетные файлы с диска**, а не доверять тому, что от них осталось в сжатом summary.
- **Четыре типа памяти, а не один:** working (контекст), semantic (устойчивые факты), procedural (готовые сценарии действий), episodic (журнал конкретных прогонов).

---

## 2. Ключевое отличие от coding-агента

У Claude Code/Codex результат инструмента — это diff, вывод команды, тест: компактный и структурированный. У browser-агента результат шага — это DOM/accessibility-tree или скриншот: огромный, шумный и (важно) **недоверенный** — это текст, который контролирует внешний сайт, а не пользователь.

Следствие: сжимать наблюдения нужно **до** того, как они попадут в working memory, а не полагаться только на позднюю компакцию истории целиком.

---

## 3. Слои памяти

### 3.1 Working memory (контекстное окно)

Текущая задача, план, последние N наблюдений — уже в сжатом виде, последние N пар «действие → результат». Триггер проактивной компакции траектории — на заполнении ~60% окна, а не на 95%.

### 3.2 Semantic memory — «база знаний по сайтам»

Аналог CLAUDE.md/AGENTS.md, но со scope на домен:

- `/memory/global/AGENTS.md` — общие конвенции агента, политика работы с секретами, общие навигационные эвристики.
- `/memory/sites/<domain>.md` — устойчивые факты по конкретному сайту: где логин, структура ключевых страниц, надёжные локаторы элементов, особенности (paywall, капча, cookie-баннер), лимиты запросов.
- Global-файл грузится всегда; site-файл — лениво, только при навигации на совпадающий домен.
- **Пишется только дистиллированными фактами, сформулированными самим агентом по итогам успешного прогона — никогда дословным текстом, скопированным со страницы.** Это прямая защита от prompt injection через содержимое сайта.

### 3.3 Procedural memory — «плейбуки»

`/memory/playbooks/<task>.md` — параметризованные пошаговые сценарии для повторяющихся флоу (логин, поиск+фильтрация, чекаут, пагинация, скачивание файла, передача капчи человеку). Обновляются агентом только после того, как сценарий отработал стабильно (≥2 успешных прогона), чтобы не переобучаться на один случайный успех. Никаких захардкоженных значений/секретов — только параметры.

### 3.4 Episodic memory — «журнал прогонов»

`/memory/episodic/<date>-<session-id>.md` — что просили сделать, последовательность действий верхнего уровня, исход, встреченные сбои, ссылки на скриншоты (пути, а не сами пиксели). По умолчанию короткоживущая; в semantic/procedural переносится только через отдельный consolidation-проход («dreaming»).

## 4. Сжатие наблюдений (специфика браузера)

- В working context не подаётся сырой HTML/DOM.
- Каждый шаг: DOM/accessibility-tree → отфильтрованное дерево релевантных интерактивных элементов → компактное текстовое представление (аналог semantic state view вместо парсинга полного дерева).
- Скриншоты сохраняются на диск, в контекст передаются только по явному запросу (vision fallback), история скриншотов в working memory не хранится.
- Сырой DOM/скриншот — «одноразовый» результат инструмента: как только агент принял по нему решение, из рабочей истории он вычищается; в episodic-лог попадает дайджест/ссылка, а не сам объект.

---

## 5. Компакция и восстановление сессии

- Периодическая транзакционная компакция траектории.
- Параллельно поддерживаемый дешёвый «дайджест сессии» (посещённые домены, прогресс задачи, ключевые решения), обновляемый на каждом шаге — чтобы не делать дорогую суммаризацию именно в момент переполнения.
- После компакции — принудительная повторная загрузка `global/AGENTS.md` и релевантного `sites/<domain>.md` с диска.
- Для длинных многошаговых флоу (например, чекаут в несколько страниц) — прогресс/текущий шаг выносится в отдельный файл состояния `/memory/state/<task-id>.md`, а не хранится только в контексте, который может быть сжат или потерян.

---

## 6. Consolidation («dreaming»)

Фоновая задача, периодически:

- сливает дублирующиеся/устаревшие записи о селекторах;
- при конфликте (сайт изменил вёрстку → старый селектор больше не срабатывает) не удаляет запись молча, а помечает её `unverified since <date>`;
- ревалидирует playbook/site-файл, если он не использовался N дней или последний раз не сработал — статус `verify before use` до следующего успешного подтверждения.

## 7. Риски (специфичные для browser-harness)

|Риск|Почему критично именно для browser-агента|Митигирование|
|---|---|---|
|**Prompt injection через контент страницы**|Сайт — недоверенный источник текста, который может выглядеть как инструкция|Semantic/procedural память пишется только дистиллированными фактами от самого агента, не дословным текстом со страницы; первая запись нового site-файла — с ревью человеком|
|**Утечка credentials/PII в файлы памяти**|Cookies, токены сессии, данные форм легко случайно попадают в снимки состояния|Явный excl-лист секретов; секреты никогда не пишутся в `/memory`, только ссылка на vault|
|**Отравление памяти (memory poisoning)**|Плейбук автоматически исполняется в будущих сессиях — если он «отравлен», ошибка воспроизводится многократно|Staged trust: новый playbook стартует как `unverified`, промоутится после N чистых прогонов; необратимые действия (оплата, удаление) всегда подтверждаются человеком независимо от памяти|
|**Дрейф селекторов / вёрстки сайта**|Главный источник «уверенно неправильных» действий агента|TTL/staleness-политика из п.6 + автоматический fallback на визуальный/LLM-поиск элемента при провале селектора|
|**Раздувание контекста DOM/скриншотами**|Основной источник затрат токенов и деградации качества в долгих сессиях|Агрессивное посошаговое сжатие наблюдений (п.4), а не надежда на позднюю компакцию|
|**Утечка scope между сайтами**|Инструкции для одного домена случайно применяются на другом|Строгий per-domain namespacing, авто-загрузка только совпадающего `sites/<domain>.md`|
|**Потеря состояния многошаговой транзакции при компакции**|Например, разрыв посреди чекаута|Внешнее состояние `/memory/state/<task-id>.md`, не полагающееся только на контекст диалога|

## 8. Структура каталогов

```
/memory
  /global/AGENTS.md              — общие политики и конвенции агента
  /sites/<domain>.md             — semantic-память по сайту (лениво грузится)
  /playbooks/<task-name>.md      — procedural-сценарии
  /episodic/<date>-<session>.md  — журналы прогонов, короткий TTL
  /state/<task-id>.md            — вынесенный прогресс для долгих многошаговых задач
  index.md                        — верхнеуровневый индекс: что где лежит, когда обновлялось
```

## 9. Политика загрузки

- Старт сессии: всегда `global/AGENTS.md` + `index.md`.
- При навигации на домен X: лениво подгрузить `sites/X.md`, если нет — создать заготовку после завершения задачи.
- При запуске задачи известного типа: подгрузить соответствующий `playbooks/<task>.md`.
- Episodic-логи никогда не подгружаются массово — только по id, при явном разборе инцидента.

---

## 10. Этапы внедрения, зависимости

1. **Фаза 0 — сжатие наблюдений + ограниченная working memory.** Без этого всё остальное бессмысленно: любые записи в semantic/episodic будут зашумлены сырым DOM.
2. **Фаза 1 — semantic per-site память с ревью человеком на первую запись.** Зависит от Фазы 0.
3. **Фаза 2 — procedural playbooks со staged trust.** Зависит от Фазы 1 (сценарии строятся на проверенных фактах о сайте).
4. **Фаза 3 — episodic-журнал + вынесенное состояние задачи + компакция-как-транзакция.** Вынос состояния (`/memory/state`) имеет смысл делать рано и параллельно с Фазой 1–2, так как это дёшево и сразу устраняет класс багов с потерей прогресса.
5. **Фаза 4 — consolidation («dreaming») + TTL/ревалидация.** Зависит от накопленного объёма данных из Фаз 1–3 — без них сливать и ревалидировать нечего.

Критический путь: 0 → 1 → 2 → 4, с 3 частично параллельно 1–2.
